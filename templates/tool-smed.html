What if the machine is the only state you need?

{{.Principle}}

A machine already knows what is installed on it, and Tailscale already knows which machines exist and how they are tagged. smed configures servers from plain Go: it reads each machine, shows you a plan, then applies it. No inventory file, no interpreter on the target, no state file anywhere.

Standing on Ansible and Terraform

Ansible gets one thing right: it looks at a machine before it acts on it. Terraform gets another thing right: it shows you a plan before you commit to it. Between them they made it normal to describe servers in version control instead of logging in and typing.

Neither does both. Ansible reads the world but runs a list of tasks with no plan to review first. Terraform plans, but against a state file instead of the world, and the state file drifts, needs locking, and needs its own commands to repair. The thing that was meant to give you confidence becomes the thing you are most afraid of.

smed does both, with one source of truth. A plan is a live read of the real machines and a diff against what you declared. "What would change" and "what has drifted" are the same question, asked at different times.

What you get by asking the machine

A plan you can trust

Every module reads, diffs, applies and verifies, and reading never changes anything. Plan never calls Apply, so it is safe against production, on a schedule, any time.

Explain, offline

Explain answers why a step exists, what it depends on and what would make a handler run, from the code alone, without touching a network.

A real graph

Independent steps run concurrently and every host runs on its own, so a slow host never holds up a fast one. A handler is just a step that runs if the steps it watches changed something.

Secrets stay where they live

The repo holds a reference like op://Engineering/web-app/api-key, not an encrypted blob. It is resolved once, at run time, from 1Password, pass or any command that prints a secret.

A playbook is a Go function

func webServers() *smed.HostSpec {
	return smed.Tag("web").
		Run(apt.Installed{Name: "nginx"}).
		Run(file.Content{Path: "/etc/nginx/conf.d/app.conf", Data: conf, Mode: "0644"}).
		Notify("restart-nginx").
		Handler("restart-nginx", service.Unit{Name: "nginx", Active: true}).
		Owns("/etc/nginx/conf.d/*") // delete any conf file not declared here
}

smed.Tag("web") is every machine tagged tag:web in your tailnet. No playbook type to learn and no registry: go run . is the dispatcher, and a module is any Go type with five methods.

Machines are made the same way. On Hetzner, a plan for a server that doesn't exist yet reads:

+ create vt100: cx22, hel1, debian-13, €4.59/month, ports 80, 443 open, SSH key me (uploaded), joins the tailnet as tag:vt100

Use Ansible if

You want the ecosystem. Thousands of modules and roles, and a team that already reads YAML. smed ships six modules: file, apt, service, user, ufw and command.

Your sudo asks for a password. smed needs passwordless sudo today.

Your machines aren't on Tailscale. Plain SSH works, but host keys aren't pinned yet; Tailscale's own tunnel is what makes that safe today.

Where it stands

Validated against a real fleet over Tailscale, not just unit tests. The bet underneath it, a pushed Go binary over one multiplexed connection instead of a Python round trip per task, was measured first: about 270 times faster on 15 hosts and 25 commands.

  • done Inventory and transport from the tailnet, connection rules and sudo.
  • done Plan, drift and explain, handlers, rolling batches with health checks, and Owns/Receipts.
  • done Secrets from 1Password, the environment or any command, and servers on Hetzner.
  • deferred Removing one declared thing, password sudo and SSH host-key pinning.
