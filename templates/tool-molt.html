What if DuckDB is the only engine you need?

{{.Principle}}

DuckDB showed that a lot of analytics fits in one process on one machine. molt asks what a SQL project needs around it when DuckDB is the whole stack: it builds a folder of plain SQL into a DuckDB database, in dependency order, with tests, in one transaction, and knows where every column comes from and what a change will touch before it runs.

Standing on dbt and SQLMesh

dbt made it normal to treat SQL as software: models as SELECTs in version control, tests as queries, a dependency graph instead of a pile of scripts. SQLMesh added plans, column-level lineage and a clear answer to whether a change is breaking. molt borrows all of those ideas.

Both are built for a harder problem than molt's: the same project on Snowflake, BigQuery, Postgres, DuckDB and more. Serving every engine takes a layer of its own: a project config and profiles, templating or macros, a SQL parser that understands each dialect. That layer is what makes them portable, and it is good engineering.

molt makes the opposite trade. It supports one engine, so it can let that engine do the work. It owns only what DuckDB can't know by itself, which files exist and the order to run them in, and asks DuckDB for everything else.

What you get by trusting the engine

All or nothing

Every run is one transaction: models, tests and bookkeeping together. A failing model or test rolls it all back, so readers never see half a rebuild or data that failed its tests.

DuckDB is the compiler

molt check binds every model with DuckDB's own binder, against the real schemas of the models upstream, without reading any data. New DuckDB syntax works the day you upgrade.

Plain SQL in and out

Models are SELECTs you can paste into any DuckDB client. molt compile prints the whole build as one script that runs without molt. There is nothing to be locked into.

No state outside the data

What was built, its columns and their lineage are written to the database itself, in the same transaction as the data, so the two can never disagree. One binary, no Python, no server.

A project is a folder

init.sql                         settings, secrets, variables, macros
models/shop/orders.sql           one SELECT per model → shop.orders
models/shop/order_items.sql      a view: "-- @kind: view" at the top
models/shop/customers.sql
models/shop/customer_revenue.sql
tests/orders_unique_id.sql       passes when it returns zero rows

No dependencies to declare and no YAML. A typo is caught by the binder before anything runs, with the line number from the model file:

$ molt check
✓ shop.customers (4 columns)
✓ shop.orders (5 columns)
✓ shop.order_items (5 columns)
✗ shop.customer_revenue: Binder Error: Table "c" does not have a column named "contry"

LINE 5:     c.contry,
            ^^^^^^^^
1 of 4 models failed to bind

Use dbt or SQLMesh if

You run more than DuckDB. molt is DuckDB only; that is what keeps it this small.

You want the ecosystem. Packages, a documentation site, hosted runs, integrations with catalogs and BI tools, and a community that has answered most questions already.

You need incremental models today. They are next for molt, and not there yet.

You need a platform. Roles, approvals and a hosted catalog belong to one, and molt isn't one. It is a command; cron or a systemd timer runs it.

Know what a change touches

molt asks DuckDB for the bound plan of each model and follows every output column down to the columns it reads. Because the plan comes from DuckDB's own binder, SELECT *, GROUP BY ALL and macros resolve exactly as they run, with no dialect to guess. Each column also gets a fingerprint of what it computes, through every model upstream, recorded with the build.

molt plan compares the project with what is built, column by column. Here a change to how quantity is computed reaches one column two models away, and nothing else:

$ molt plan
~ shop.order_items                     modified, breaking
    ~ quantity                 modified
~ shop.customer_revenue                affected, breaking
    ~ revenue                  modified ← shop.order_items.quantity

2 models changed, 2 models unchanged

molt run prints the same plan before it builds, and molt lineage <model> <column> traces one column all the way to its sources.

Where it's going

The goal is what a DuckDB project needs from dbt and SQLMesh, with DuckDB doing the hard parts.

  • done Column-level lineage. From DuckDB's own bound plan, so every column resolves exactly as the query runs.
  • done molt plan. What changes, column by column, and whether it is breaking for anything downstream, before anything is built.
  • next Incremental models. Append or merge new rows, with the intervals that were built recorded in the database, in the run's transaction, and a full refresh only when the plan says a change is breaking.
  • planned Unit tests. A few rows in, the rows you expect out, per model.
  • planned Environments. Dev and prod in one file, as schemas of views over the same tables. No copies, instant rollback.
  • planned Lineage out. Export to JSON and OpenLineage, for the catalogs and tools you already use.
