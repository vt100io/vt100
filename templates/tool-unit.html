What if systemd is the only runtime you need?

{{.Principle}}

A statically compiled binary runs on any Linux host as it is, and every Linux server already runs systemd as PID 1. unit takes a short description of what your app needs, writes hardened systemd units for it, ships the binary over SSH and activates it. No containers, no daemons.

Standing on containers

Containers made it normal to ship a program with everything it needs, isolated from the rest of the machine, and to run the same image on a laptop and in production. For a program with a runtime, a Python app or a JVM service, that solves a real problem.

A static binary doesn't have the problem. It has no runtime to ship and no libraries to pin. Put it in a container anyway and you add an image to build, a registry to push to, a base image to keep patched and usually a daemon to run it, and get nothing for it.

The isolation was never the container's own. It is the kernel's: namespaces, cgroups, seccomp. systemd has spent two decades exposing the same primitives to the services it runs. What it lacks is ergonomics: a correctly hardened service is 40 lines of directives before anything is about your app. unit writes them.

What you get from PID 1

Default deny

No outbound network, a read-only filesystem, no capabilities and no executing from state. You allow what the app needs, one line each, and unit audit runs systemd-analyze security to check.

Secrets as files

A script you commit says where each secret lives. unit fetches them at deploy time, and systemd hands them to the service as files in a private, memory-backed directory, never in its environment.

The binary CI built

Name a CI check and unit deploys only commits that passed it, and only a binary byte-identical to the one CI built. Two independent builds must agree, so neither a compromised CI nor a compromised laptop can ship a binary alone.

Every deploy on record

Who deployed what, from where, how long it took and how it went, one JSON line per deploy on the server. A version that fails its health check is rolled back automatically.

This site is a unit

vt100.io is deployed with these lines of unit.toml:

name       = "vt100"
executable = "bin/vt100"
port       = 8080
domain     = "vt100.io, www.vt100.io"

ci_check    = "punchcard/ci"
ci_checksum = "punchcard/sha256"

[server]
host = "vt100"
user = "deploy"

[resources]
memory_max = "128M"

From them unit writes a socket, a Caddy config and a service unit with 38 settings. An excerpt:

Use containers if

Your app has a runtime. unit ships static binaries and nothing else. A Python or JVM app is what images are for.

Many people deploy. unit deploys from wherever you run it. With a team, deploys belong in CI with isolated jobs and a deploy identity no build can read.

You need an orchestrator. unit puts one app on a server you name. Scheduling across a fleet is someone else's job.

Every deploy, on the server

unit history reads the record. Over Tailscale SSH, who and from where are answered by the server's own tailscale whois, not claimed by the laptop:

$ unit history
WHEN              APP    VERSION            RESULT  CI       BINARY      WHO            FROM   TOOK
2026-11-14 23:05  vt100  8cc5a1f → 4f44815  live    success  same as CI  stianh@github  elcap  17s

Your app does three small things in return: it uses the socket systemd opens, says READY=1 when it serves, and pings the watchdog. In Go that is a dozen lines of the standard library.
